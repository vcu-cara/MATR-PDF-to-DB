# From CSV Files to a Relational Database: Managing Questionnaire Metadata at the Mid-Atlantic Twin Registry

## Abstract

### Background

Beginning in 1975, the Mid-Atlantic Twin Registry (MATR) collected voluntary data from more than 60,000 twins and continues to administer questionnaires as part of ongoing research. MATR stores participant responses in a secure database where each questionnaire is a table and each response is a column. The information that describes the questionnaires lived in the original PDF and Word documents and, more recently, in comma-separated values (CSV) files. To find relevant data, a researcher would search decades of questionnaires by hand. The PDF2CSV website made extraction faster, but extraction was still incomplete; every correction still happened in CSV files, these flat files could not represent shared questions or the dependencies between them, and publishing a new questionnaire to the MATR Dashboard, a website displaying extracted questionnaire metadata, still required changing the source code and redeploying the website.

### Objective

The objective of my externship project was to build a system that stores MATR questionnaire metadata in a structured way and let staff carry it through extraction, review, and publication without writing code. I was responsible for the database and the administrative website that staff used to manage it. Connecting the MATR Dashboard to the new database was a separate project.

### Methods

Requirements were defined before anything was built, including what the metadata needed to do, who would read and write it, what the project would leave unchanged, and what the definition of done was. A normalized relational database was then designed in PostgreSQL (REF) and hosted on Supabase (REF). An administrative website was built in R (REF) with the Shiny framework (REF) so that staff could manage the database without writing structured query language (SQL). Questionnaire PDFs uploaded to the website were read by Gemini Flash 3.8 (REF), a large language model (LLM). The model's output was saved as a draft for staff to correct and complete. Before a change was made, the website showed staff exactly what it would do, and afterward the database kept a permanent record of it. Validation rules were placed in both the database and the website.

### Results

The finished database held 22 linked tables divided into two groups. The catalog group, 19 tables, covered registries, studies, investigators, questionnaires, waves, questions, variables, answer choices, tags, and measurement scales, and it was the only part of the database a researcher could see. The staff group, 3 tables, covered staff accounts, extractions, and the history of every change. One further table, kept up to date by the database itself, supported searching for questions by their meaning. The schema kept the questions, answer choices, and identifiers the flat files held, stored each printed wording once however many questionnaires used it, linked each follow-up question back to the question it depended on, and made room for five kinds of metadata that the flat files had never captured. On the website, staff uploaded a questionnaire PDF, Gemini read it, and the model's output became an extraction draft that staff finished in place and then pushed into the database in a single step that either succeeded completely or changed nothing. Staff edited existing metadata on a separate page of the same website. MATR staff used this process to enter the questionnaires already held in flat files, running the original PDFs back through the website as practice on instruments they already knew well. The database recorded each change with who made it, when, and the value of each field before and after, and validation rules stopped errors such as a duplicate variable identifier before they were written. A monitoring page reported how often staff had to correct what the model had read.

### Conclusion

Together, the database and the administrative website moved MATR's questionnaire metadata out of flat files and into a structure that can represent how questions relate to one another, and they let the people who know the questionnaires best maintain the metadata. Once the Dashboard reads from the database, a questionnaire that staff have pushed becomes visible to researchers without anyone changing source code, which means the pace of publishing will be set by how quickly staff can work through the collection. As a result, more of the registry's data can be found, and data that can be found can be requested.

## Introduction

### Research Registries

Research registries collect and maintain information from a group of participants for future scientific inquiry. An individual research study is usually designed to answer one specific question, but a registry preserves participant information and the data collected across many studies so that it can be used again in research that has not been planned yet. Because that information has to be kept for years and made available to researchers who were not part of the original study, a registry needs a secure database that protects participant level information. This matters because data collection is usually the slowest and most expensive part of research. Before analysis can begin, a researcher has to secure funding, get the questionnaire approved, recruit participants, administer the questionnaire, and collect responses. By preserving data from earlier research and making it available for archival analysis, a registry lets researchers investigate new questions without repeating that entire process (Lilley & Silberg, 2013). Many registries also follow the same participants over time, which lets researchers examine how characteristics, behaviors, and health outcomes change as people age (Hur & Craig, 2013). This longitudinal data is especially valuable for studying patterns that a single observation would not reveal. Since the same dataset can answer many different questions, one registry can support many studies without any of them collecting new data (Anderson et al., 2002; Lilley & Silberg, 2013).

### The Mid-Atlantic Twin Registry

The Mid-Atlantic Twin Registry (MATR) began as the Virginia Twin Registry around 1975, merged with the North Carolina twin registry in 1997, and added South Carolina in 1998 (Lilley & Silberg, 2013). By 2019 it had registered more than 60,000 twins, and it continued to administer questionnaires as part of ongoing research (Lilley et al., 2019). MATR focused on twins because twin pairs give researchers a natural comparison for separating genetic and environmental influences on health and behavior, a use of twins that traces back to Galton (Hur & Craig, 2013). Identical twins share all or nearly all of their genetic material, while fraternal twins share about half on average, and both kinds of pairs usually grow up in similar environments (Boomsma et al., 2002). When a trait is more alike within identical pairs than within fraternal pairs, the difference points toward a genetic influence, and when fraternal pairs are nearly as alike as identical pairs, the shared environment explains more of the resemblance (Boomsma et al., 2002). That comparison is only possible when a registry has enrolled many pairs of both kinds and kept their data over time. MATR did exactly that, and by 2012 nearly 50,000 of its registered twins belonged to complete same-sex or opposite-sex pairs (Lilley & Silberg, 2013).

### Questionnaires and Their Metadata

Questionnaire responses were one of several kinds of data that MATR maintained. The registry also held a repository of blood samples and de-identified datasets created by linking MATR records with vital statistics, the Virginia Department of Motor Vehicles, and the Virginia Cancer Registry, and each of those resources was collected, stored, and requested in its own way (Lilley & Silberg, 2013). This project concerned only questionnaire metadata, so the rest of this introduction focuses on how MATR administered questionnaires and stored their responses. A questionnaire is a predetermined set of questions used to collect data, which makes it a measurement instrument in the same way that a scale is the measurement instrument of a weigh-in. Each questionnaire is written to measure a characteristic or experience that researchers want to study, such as how often a person exercises or whether they have ever smoked. A Dictionary of Epidemiology reserves the word for a form that respondents complete themselves and calls a form that an interviewer reads aloud an interview schedule (Porta, 2014). MATR used the word in its broad sense, and this report follows MATR, because the database treated a self-administered form and an interviewer's script the same way even though they reached the respondent differently.

MATR collected questionnaire responses through mailed surveys that were optically scanned on return, telephone surveys, online surveys, and in-home interviews (Anderson et al., 2002; Lilley & Silberg, 2013). Whatever the method, every questionnaire contained predefined questions and, for most questions, predefined response options, so that every respondent was asked the same thing in the same way. Each place on a questionnaire where an answer was recorded is a variable. The word carries a different meaning in each of the two fields this report speaks to. In epidemiology, a variable is any characteristic that can take different values for different people, such as height or smoking status, while in computer science it is a named place in a program's memory whose contents can change while the program runs. This report uses a version of the first meaning, so a variable here is one place on a questionnaire where an answer was recorded. Each variable held exactly one recorded response from each participant. MATR stored those responses in a secure database, shown in Figure 1, where each questionnaire occupied its own table. Each participant was identified by a unique participant identifier, each variable occupied its own column, and each participant's recorded responses formed a row. Questions 1a through 1d of the Geno-Neurological Assessment (GNA) show how this worked in practice. Each printed question on the form became one column in the GNA table, named with the variable identifier that the data steward assigned to it.

Nothing in the response database recorded the associated question text of a column. This gap exists because response data and questionnaire metadata serve different purposes. Response data are the answers participants provided. Questionnaire metadata is everything that describes a questionnaire, its questions, and its answer choices, which includes the questionnaire title, the question text, the question number, the response options, the variable identifiers, and the instructions and other context printed around the questions. The responses are what a researcher analyzes, while the metadata is what tells the researcher that those responses exist. My externship project focused entirely on questionnaire metadata and never touched participant level responses.

### The Data Discoverability Problem

MATR accumulated questionnaire data over several decades, beginning with basic health surveys of adult twins in the early 1980s (Anderson et al., 2002; Lilley & Silberg, 2013). Preserving responses was only one part of making historical data useful, because a researcher cannot request data that they do not know exists. Contaxis et al. described data discovery as the process of learning that a dataset exists, and they separated it from data access, which is the ability to download or view the data. Both ideas belong to the FAIR Data Principles (Findable, Accessible, Interoperable, Reusable), which the National Institutes of Health has adopted (Contaxis et al., 2022). The distinction fit MATR closely, since participant responses had to stay restricted while the metadata that described them could be public. For restricted data, Contaxis et al. recommended a data catalog, which holds a description of the data and the procedure for requesting it, so that the existence of the data becomes visible without the data itself being exposed. The MATR Dashboard was meant to serve as that catalog.

Until recently, however, all of MATR's metadata lived in the original questionnaire PDF or Word document. This created a discoverability problem because a researcher can only request data that they know exists. A researcher who wanted to use MATR data had to search decades of questionnaires by hand to find relevant questions, keep a record of each questionnaire name and question number, and then send a data request to the MATR data steward, the staff member who located and pulled the matching participant data from the secure response database. This process was slow and error prone because a researcher could easily miss a relevant question, copy down the wrong question number, or confuse two questionnaires with similar names, and any of those mistakes could reach the data steward as a request for the wrong column. As a result, much of the registry's data went unused.

### Early Digitization

MATR staff began addressing this problem by saving questionnaire metadata into comma-separated values (CSV) files, which are plain text files that hold one row per record and can be opened in any spreadsheet program. At first they extracted the metadata by hand, copying the text of each question and its response options from the PDF into Google Sheets and saving the result as a CSV. This was slow because a person had to retype every question and every answer choice, and every retyped line was another chance for a transcription error to enter the record. Manual extraction was also incomplete, since staff often recorded a shortened form of a question rather than its full printed text, so that "What is your current height?" became "Height?" in the file. The extraction step improved considerably in 2025 with the creation of the PDF2CSV website. A staff member uploaded a PDF questionnaire, a large language model read it and pulled out the question text and response options, and the website returned a CSV with one row for each question and its answer choices. This was much faster than retyping, but it did not remove the manual work. Staff still had to download the CSV, open it in Google Sheets, correct anything the model got wrong, and add details the model never extracted, such as the respondent type and the variable identifier for each question. Four limitations remained, and they defined what this project needed to address.

The first limitation was that extraction was incomplete. PDF2CSV extracted question text and response options, but it left out section titles, instructions, definitions, and other printed material. Staff had to add that information by hand afterward, and anything they did not add was lost so researchers would later read the metadata without any surrounding context.

The second limitation was that extraction and editing were separate steps rather than parts of one workflow. Staff could not edit the extracted metadata inside PDF2CSV, so every correction required downloading the CSV and opening it in Google Sheets, where every variable identifier and respondent type also had to be typed in. Each handoff between tools was a point where a file could be overwritten, saved under the wrong name, or edited by two people at once.

The third limitation was the structure of the flat files themselves. Everything digitized so far lived in CSV files that together held 1,255 rows. Figure 2 shows how questions 1a through 1d of the GNA looked in that format. A flat file stores each question as an isolated row, so it cannot express the relationship between one question and another, even though that relationship is part of what a question means. The clearest case is a follow-up question that a respondent answers only when an earlier question was answered a particular way. In the flat file, "If yes, age started?" recorded nothing about which question the yes belonged to, so a researcher who landed on that row could not tell what was being asked, as Figure 3 shows. The same structure caused a second problem. Some questions appeared in several questionnaires, and each appearance was stored as a separate row rather than as a reference to one shared record, so a correction made to one copy did not reach the others and had to be repeated on every row.

The fourth limitation was that publishing new metadata required writing code. The flat files sat behind the MATR Dashboard, shown in Figure 4, the public website where researchers browsed the metadata and decided what data to request. The Dashboard read the CSV files into memory when it started, so adding a newly digitized questionnaire meant changing the website's source code and redeploying the website. Every new questionnaire therefore waited on someone who could edit the code and redeploy the website.

## Chapter 1: The Metadata Database

### Introduction

Most epidemiologists already work with the idea behind a relational database, even if they have never built one. A cohort study rarely keeps everything in a single spreadsheet. It keeps a baseline file and a follow-up file and links them through a participant identifier, rather than retyping each participant's sex and date of birth into every file. A relational database applies the same logic to every kind of information it holds. Each table describes one kind of thing, such as questionnaires, questions, or answer choices. The tables point to one another through identifiers in the same way that a follow-up record points to a baseline record.

The value of this design comes from storing each fact in exactly one place, which is what the term normalized means. In MATR's flat files, a question that appeared on five questionnaires was typed out five times, so a typo fixed in one row survived in the other four. Nothing in the files said that the five rows were the same question. In a normalized database the question text is stored once and each questionnaire points to it, which means a correction reaches every questionnaire at the same moment. The same structure lets the database record relationships that a flat file has no column for, such as the fact that "If yes, age started?" belongs to the question printed just above it.

A database also enforces rules that a spreadsheet cannot. It can hold rules about the metadata itself, such as refusing a variable identifier that is already in use within a questionnaire. It applies those rules to every change, whoever or whatever makes it. Because everyone reads and writes the same database, there is never a question of which copy of a file is current. Every change can be stored alongside who made it and when. For a registry whose metadata will be maintained by different staff over many years, these properties matter far more than the convenience of opening a file in a spreadsheet program. The cost is that a relational database is harder to change by hand. Chapter 2 describes how the project paid that cost.

### Methods

Before any table was built, the requirements for the database were defined by asking what MATR needed the metadata to do, who would read and write it, what the project would deliberately leave alone, and what would count as done. The answers were treated as the definition of done, and the finished database was measured against it. The database was then built in PostgreSQL, a widely used open source relational database system, and hosted on Supabase, a service that runs PostgreSQL databases and provides secure access to them over the web. Every table, rule, and function was written as a script in structured query language (SQL), the language used to read and change a relational database, so that the entire database could be rebuilt from those eight scripts on a new server. The design document for the database, and a script that generates technical documentation of every table and column directly from a running database, are listed in the Appendix.

The database was required to hold metadata for every questionnaire MATR had administered, including those that had not been digitized yet, so that a researcher would see the full potential of the registry rather than only the part that had made it through the digitization pipeline. Within a questionnaire, the metadata was required to sit as close as possible to the way the respondent saw it. Section headings, printed instructions, the link between a follow-up question and the earlier question it depended on, and every place where the respondent could write or mark an answer were all to be preserved. Because only a small portion of the metadata had been digitized, the schema also had to accept what existed at the time while staying flexible enough to absorb the much larger volume of historical and future metadata that would arrive later.

Room was also required for five kinds of metadata that the flat files had never captured. Two of them described when and how widely a questionnaire was used. The number of respondents was to be stored for each wave, since that count tells a researcher whether a wave's data are worth requesting at all, and a questionnaire answered by forty people supports a very different study than one answered by four thousand. The date each wave of a questionnaire was administered was also to be stored.

One described what a question measured. Each question was to record whether it belonged to a published measurement scale, which is a fixed set of questions scored together to produce a single measure, and which scale or scales it belonged to. A researcher who knows that a group of questions forms a validated scale can score them the way the scale's authors intended instead of treating each question on its own. The last two described the context around a questionnaire. The study each questionnaire belonged to and the investigator who led that study were to be recorded, so that a researcher who found a promising instrument would know whom to contact about it. An anonymous upvote count was also to be stored, so that staff could gauge which questionnaires researchers were interested in and decide which instruments to digitize next.

Three groups of people were identified whose needs shaped the design. Internal users were defined as the MATR staff responsible for digitizing and managing registry metadata. They were to sign in to the administrative website to add, update, and remove metadata, and they were the only users permitted to write to the database. External users were defined as academic and clinical researchers seeking secondary data, including twin researchers, epidemiologists, and graduate students, since MATR welcomed researchers from all institutions and fields (Lilley & Silberg, 2013). They were to reach the public Dashboard through a standard web browser without signing in, with read only access, so that they could search, filter, and explore five decades of questionnaire metadata before submitting a formal data request. The only thing they could write was an upvote, which was deliberately kept anonymous. The data steward was identified as the key downstream stakeholder. A list of relevant metadata exported from the Dashboard by a researcher was designed to contain variable identifiers, which would be used by the steward to locate and pull the matching participant data from the separate secure response database. The exported file was therefore treated as the point where the metadata database and the response database met, even though neither one ever read the other.

Several boundaries were set on purpose. Questionnaires were treated as permanent historical documents, so version history of the instruments themselves was not tracked. Researchers were assumed to use standard modern web browsers, and MATR staff were assumed to have basic computer literacy. Classifying questions by subject was left for later work. The earlier three column categorization of category type, domain, and variable type was not carried into the database, and its intended replacement is Medical Subject Headings (MeSH), the controlled and hierarchically organized vocabulary that the National Library of Medicine produces for indexing and searching biomedical literature (National Library of Medicine, n.d.). MeSH would let researchers search the registry with the same terms they already use to search the published literature, an approach recommended for medical data repositories (Contaxis et al., 2022). No participant responses or identifying information were placed in the database, and it was kept completely separate from the secure database that held responses. The data request process was also left unchanged, so a researcher who found relevant data on the Dashboard would still submit a request to the data steward, who would fill it through existing channels. To enforce the separation between public and staff information, access rules were written into the database itself, so that anyone could read the metadata tables while only signed in, active staff could read the administrative tables. The database was to be considered done when the schema retained every piece of metadata the flat files already held, other than that earlier categorization, including questionnaire titles, abbreviations, and respondent types such as Adult, Parent, and Child. It also had to support the five additional kinds of metadata described above and had to link a question that continued or depended on an earlier one back to that earlier question. Once connected, the Dashboard had to be able to use the database as its back end and show all available metadata without anyone editing its source code when a new questionnaire was added.

### Results

The finished database held 22 linked tables divided into two groups that served the two groups of users. The first group, 19 tables, was the catalog. It held the metadata itself and covered registries, studies, investigators, respondent types, questionnaires, waves, the printed content of each questionnaire, variables, answer choices, tags, measurement scales, and a record of each stored questionnaire PDF. These were the tables the Dashboard would read from, and they were the only part of the database a researcher could see. The second group, 3 tables, held the staff's work and covered staff accounts, extractions, and the history of every change. These tables existed only for the administrative website, and they made it possible to say who made any change to the metadata and when. Keeping both groups in one database meant that a change and its history record were written together, so the database could never reach a state in which the metadata had changed but the record of who changed it had not. One further table, written only by the database itself, held the information needed to search for questions by meaning, which is described later in this section. The schema was organized from the largest thing to the smallest. A registry held studies, a study held questionnaires, and a questionnaire was given in one or more waves, each wave being one round of data collection. Everything printed on a questionnaire was stored as a component, and a component was one of nine kinds: a section heading, a question, an instruction, an introduction, a definition, a note, an interviewer's script, a grid, or a group. A grid is a lead-in printed once above several questions that finish its sentence, such as "In the past week I have" followed by a list of items, and a group holds blocks that belong together under no printed heading. Each distinct wording was stored exactly once, word for word as printed apart from capitalization, no matter how many questionnaires printed it or how often. A separate record, called a placement, said where a particular questionnaire printed that wording, which section, grid, or group it sat inside, and in what order. Because the wording was shared and the placement was not, a correction to a question's text reached every questionnaire that printed it, and the database could report every questionnaire that had asked the same question.

For a follow-up question, the placement also recorded which earlier question it depended on. This link let "If yes, age started?" carry a connection back to the question its yes belonged to, which the flat file in Figure 3 could not do. The database required the two questions to be in the same questionnaire and refused any chain of dependencies that circled back on itself. The printed routing instruction itself, such as "go to question 10", was not stored, because a researcher needs to know that one question hangs off another, not the wording that sent the respondent there.

Each place where an answer was recorded was stored as a variable, which carried the variable identifier that the data steward used to find the matching column of responses. MATR staff call this identifier the MATR ID. A variable was either open-ended, meaning the respondent wrote in a number, some text, a date, or a time, or closed-ended, meaning the respondent chose from a printed list. A question with two blanks, such as one for feet and one for inches, had two variables. Each answer choice, such as "yes" or "never", was stored once for the whole registry in a standard form, and each variable recorded the order in which it printed its choices and the code under which each choice was stored in the response data. When a second wave of a questionnaire was entered, the database reused the questions and variables the questionnaire already had and recorded only which questions the new wave asked and how they were numbered. Measured against the definition of done, the schema retained everything the flat files held other than the earlier categorization, including questionnaire titles, abbreviations, and respondent types, and it linked each follow-up question to the question it depended on. It also gave each of the five new kinds of metadata a place, as Table 1 shows.

Two features were added that help researchers narrow a search. The first was tags. A tag is a short label of one of three kinds: a subject, meaning the person an answer is about, such as "twin" or "mother"; a time frame, such as "past 30 days" or "lifetime"; or a unit, such as "pounds". A tag could be attached to a question, to a variable, or to a single answer choice, and each tag was written one standard way so that a filter for "past 30 days" would find every question about that period however the form had phrased it.

The second was search by meaning. For each question the database stored an embedding, which is a list of 384 numbers, produced by a small language model, that represents the meaning of a piece of text, so that two texts about the same thing receive similar numbers even when they share no words. The text behind each embedding was the question's own wording, the lead-in it shared with neighboring questions, the question it depended on, and the heading of its section. The database refreshed these embeddings on its own whenever questionnaire content changed. A researcher's search phrase can be converted in the same way and compared against every question, so that a search can match a question that never uses the searcher's words. Search by meaning helps a researcher find questions by topic, but it is not a controlled vocabulary such as MeSH and does not replace one.

Access rules written into the database enforced the separation between the two groups of users. Anyone could read the catalog. Only signed in, active staff could read the staff tables. Only the administrative website could change anything, with one exception, the anonymous upvote. Each questionnaire PDF was stored once, and after a questionnaire was pushed into the catalog its PDF could be linked from the Dashboard, so that a researcher could see the form exactly as respondents saw it. The PDF of a draft that had not been pushed stayed unlisted. Figure 8 summarizes who could read and write each part of the system.

The database itself enforced the rules that must never be broken. A variable identifier could not be used twice within a questionnaire. Only a question could have variables or be asked in a wave. A closed-ended variable had to have at least one answer choice, and an open-ended variable had to say what kind of answer it took. Each wording, each answer choice, and each tag could exist only once. The history could be added to but never changed, staff accounts could be deactivated but never deleted, and the content of an extraction could not be altered once it had been pushed.

MATR did not load the 1,255 rows from the flat files into the schema directly. Instead, staff entered those questionnaires through the administrative website, as Chapter 2 describes, which meant that everything in the database arrived through the same validation and review that every future questionnaire would go through.

### Conclusion

The database addressed the third limitation of the earlier workflow, which was the flat file structure. A flat file could only store each question as an isolated row, so it could not say which earlier question a follow-up depended on, and it forced the same correction to be made on every copy of a shared question. The normalized schema stored each fact once and recorded the relationship between questions directly, which meant a researcher who landed on a follow-up question could see what it continued and a correction had to be made in only one place. The trade was that a schema with 22 linked tables could be changed safely only by someone who understood how its tables depended on each other. On its own, the database would have made publishing harder rather than easier, and that was the problem the administrative website solved.

## Chapter 2: The Database Administrative Website

### Introduction

A normalized database solved the storage problem, but on its own it would have made the publishing problem worse. The flat files could at least be opened in Google Sheets, while a schema with 22 linked tables could be changed safely only by someone who knew how the tables depended on each other and how to write SQL. If staff had needed to write SQL to add a questionnaire, MATR would have traded a website that needed a programmer for a database that needed one. The administrative website existed so that the people who knew the questionnaires best could maintain the metadata without writing a single line of code.

### Methods

The website was written in R using the Shiny framework, which turns R code into an interactive web application, and it was connected to the Supabase database over the web. It was deployed on Posit Connect, and the exact version of every R package it used was recorded with renv so that the same website could be rebuilt later. Staff signed in with an email address and a password, or with a sign-in link sent to their email, and only people listed as active staff in the database were admitted. Automated tests were written for the website and the database and were run against a separate test database, so that new features could be checked without touching the live metadata. By the end of the project there were more than 600 of these tests, and they ran automatically each time a change was submitted to the project's code repository. The design was based on three decisions, which were to keep extraction and editing in one place, to show staff what a change would do before it was made and to record it afterward, and to catch mistakes before they were written rather than after a researcher found them.

The first decision was made in response to the second limitation, in which every handoff between PDF2CSV, a downloaded file, and Google Sheets was a chance for a file to be overwritten, saved under the wrong name, or edited by two people at once. The website was therefore designed so that extraction, correction, and completion all happened inside it. Each uploaded PDF was sent to Gemini through the Gemini application programming interface (API), which is the channel one program uses to send a request to another, together with a written set of extraction instructions. The instructions were completed from the database each time they were used. The subjects, time frames, units, and standard answer choices already in the database were read and inserted into the instructions, together with the nine kinds of component the database allows. In this way the extraction was kept in the same vocabulary as the database, so that every block returned by the model had a matching place in the schema, and a new subject or time frame added by staff reached the model without anyone editing the instructions. The model was instructed to copy every question, answer choice, and instruction word for word, which addressed the shortened text that manual extraction had produced. The few exceptions were narrow, such as a table column headed only "Sex", which was written out as the question it stood for. The model was also instructed to leave out anything that identified a person, such as blanks for names, addresses, and dates of birth, along with handwriting, marks made on the form after printing, and anything covered by a redaction.

Reading was arranged around what the model could do reliably. Because the model can write only a limited amount in one answer, each questionnaire was sent two pages at a time, with the requests made at once and the answers joined afterward. The website then checked the joined result against the rules it would later apply to a staff member's draft. If the checks found problems, the model was asked to read the questionnaire once more and was told what the problems were, and whichever reading had fewer problems was kept. Reading took a minute or more, so it ran in the background while staff carried on with other work. Figure 9 traces these steps. The model did not read variable identifiers from the questionnaire itself. They came instead from an optional second file listing variable names and answer codes, which the model matched to the variables it had found, or they were supplied by staff afterward. Whenever the instructions were revised, the change was checked by having the model read the GNA, whose correct extraction had been verified by hand, and comparing every field of the result against that reference. The model's output was saved as an extraction draft for staff to finish in place, and the model's original reading was kept unchanged beside the staff's corrected copy so that the two could later be compared. Changes to metadata that already existed were made on a separate page of the same website, so there was no file to download and nothing to retype into a spreadsheet.

Under the second decision, staff were shown what a change would do before it was made, and every change was recorded afterward. Because the team that maintained the metadata was small, a second person's approval was not made a formal step, and any active staff member could make any change. A draft simply stayed a draft, visible to every staff member on the Drafts page, until someone pushed it, which left room for a colleague to look it over first. Three safeguards protected each change. First, before a draft was pushed into the database, the website ran the push as a trial and reported exactly what it would add and what it would reuse. The trial used the same database function as the real push and then undid its own work, so the preview could not differ from the result. Second, before an edit or a deletion was applied, the website listed every place the change would reach, and it would not apply a deletion while other records still stood in its way. Third, the database kept a history that could be added to but never altered. A mistake that slipped through could still be undone, because a wave could be emptied and its questionnaire read again from the stored PDF.

Under the third decision, validation was placed where it could stop a mistake before anything was written, rather than leaving it to be discovered later by a researcher. The value of catching errors this early is easiest to see by imagining the alternative, because a duplicate variable identifier that reached the Dashboard would have sent the data steward to the wrong column. Validation was split between two layers. Rules that must never be broken, whoever or whatever writes to the database, were placed in the database itself, while checks that only made sense for a draft in progress were run by the website before the draft could be pushed. Pushing a draft, applying an edit, and emptying a wave were each written as a single function inside the database, so that a change was applied completely or not at all.

The website was to be considered done when staff could add, update, and delete metadata through it, with validation catching mistakes before anything was written, and when a new questionnaire could go from PDF to published metadata without anyone editing code. These were the conditions the earlier workflow could not meet, since PDF2CSV offered no way to edit or review what it extracted and every new questionnaire depended on a programmer to reach the Dashboard.

### Results

The website became the place where MATR staff added new content to the database and edited the metadata already there. Table 2 lists its pages.

*Table 2.* The pages of the administrative website.

| Page | What staff do there |
| --- | --- |
| Home | See how many extraction drafts they have in progress and how many changes have been made, and open any other page. |
| New Extraction | Upload a questionnaire PDF for Gemini to read, or start an empty draft to type in by hand. |
| Drafts | Find every extraction that has not been pushed yet, their own and their colleagues'. |
| Edit Extraction | Review and correct a draft, supply its variable identifiers, choose where it belongs, preview the push, and push it. |
| Metadata | Add, update, or delete metadata already in the database, empty a wave, or have a wave read again from its PDF. |
| History | See every change made through the website, newest first. |
| AI Monitor | See how often, and where, staff correct what the model read. |

To add a questionnaire, a staff member uploaded the PDF on the New Extraction page, the website sent it to Gemini, and the website saved the model's output as an extraction draft. Staff finished the extraction on the Edit Extraction page, which showed the questionnaire as an outline of its sections and questions beside the details of whichever block was selected (Figure 10). There they corrected the text, filled in what the extraction missed, marked each block as checked, and added the variable identifiers that previously had to be typed into a spreadsheet. Identifiers could come from the optional second file read at upload, which could be a PDF, a CSV, or a text file; from earlier waves of the same questionnaire already in the database, where a question with the same wording passed its identifiers on; or from typing. The page listed every problem that still stood between the draft and the database, such as a variable with no identifier or a question with no variable, and took the staff member to each one in turn. The model read the number printed beside each question, and the website numbered the questions in order.

The page was built for more than one person working over more than one sitting. A draft was saved automatically after a minute without activity. If a second staff member opened a draft that a colleague already had open, the website asked whether to take it over, and it refused to save over a copy that someone else had saved more recently, which closed off the two-people-at-once problem that the spreadsheet workflow had left open.

>
> *Figure 10.* The Edit Extraction page of the administrative website, where staff corrected and completed the metadata that Gemini extracted from a questionnaire PDF.

When a draft was ready, the staff member chose the registry, study, questionnaire, and wave it belonged to and pushed it. Before the push, the website showed a preview of what would be added and what would be reused. The push then wrote the whole questionnaire in one step. Wordings, answer choices, and tags that the database already held were reused rather than duplicated, the wave's PDF was attached, and the push was written to the history. If any part failed, nothing was written.

Staff changed existing metadata on the Metadata page (Figure 11), which asked them to complete a sentence in plain language, "I want to add, update, or delete a registry, study, questionnaire, wave, question", and then helped them find the record, change it, and see everywhere the change would reach before applying it. A change was applied at once. The same page could empty a wave, questionnaire, study, or registry, which removed its content while keeping the record itself, and it could send a wave's stored PDF back to Gemini to be read again with the latest instructions.

>
> *Figure 11.* The Metadata page, where staff changed metadata already in the database by completing a sentence and reviewing what the change would reach before applying it.

Whenever a change was applied, the database recorded who made it, when, and what it did. For an edit, the record held each field that changed with its value before and after. For a push or an emptying, it held counts of what was added or removed. Because that record lived in the same database as the metadata, the database wrote the change and its record together. The History page (Figure 12) listed these records, newest first, so staff could trace any piece of metadata to the person who entered it.

> **[Figure 12 placeholder]** Suggested content: a screenshot of the History page with one change opened to show each field's value before and after.
>
> *Figure 12.* The History page, which lists every change made through the website and, for each one, who made it, when, and the value of each field before and after.

The database itself enforced the rules that must never be broken, such as refusing a variable identifier already in use within the same questionnaire, refusing a variable attached to anything other than a question, and refusing a follow-up question that depended on a question in a different questionnaire. The website checked the rest before staff could push a draft. Together, these checks stopped the errors most likely to mislead a researcher or send the data steward to the wrong column at the point of entry.

Because the model's original reading was kept beside each corrected draft, the website could measure the model's work. The AI Monitor page (Figure 13) reported how often staff corrected what the model had read, how that rate changed over time and from one version of the instructions to the next, and which corrections came up again and again. A correction that staff had to make repeatedly was the clearest sign of something the instructions should say differently, so the page turned staff review into evidence for improving the extraction.

>
> *Figure 13.* The AI Monitor page, which reports how often staff corrected the model's reading, by version of the extraction instructions and over time, and which corrections recurred.

With the database and the website in place, adding a questionnaire became a matter of uploading the PDF, editing the draft, and pushing it. The questionnaires that MATR had already digitized went through this same cycle. Rather than loading the 1,255 rows from the flat files directly into the database, MATR staff ran the original PDFs through the extraction page and worked each questionnaire through the website from extraction draft to push. Staff used these questionnaires as practice because they already knew them well, which let them judge whether an extraction draft was right and learn the website on instruments where a mistake would be easy to spot. This also meant the existing metadata entered the database through the same validation and review as every questionnaire that would follow it, rather than bypassing both through a direct import.

### Conclusion

The administrative website addressed the remaining three limitations of the earlier workflow. Staff could fill in what extraction left out in the same place they corrected it, and the extraction instructions captured the instructions, definitions, and section headings that PDF2CSV had dropped, which closed the gap left by incomplete extraction. Extraction, correction, and completion happened in one workflow instead of being passed between a website, a downloaded file, and Google Sheets, which removed the handoffs where files had been overwritten or saved under the wrong name. Most importantly, publishing a questionnaire no longer depended on a programmer changing the Dashboard's source code and redeploying it. The website relied on previews, automatic checks, and a permanent history to keep the metadata accurate. As more of MATR's paper questionnaires are digitized, the same cycle of extraction, review, and push will handle each one, so the pace of publishing will be set by how quickly staff can work through the collection rather than by how quickly a programmer can redeploy a website.
